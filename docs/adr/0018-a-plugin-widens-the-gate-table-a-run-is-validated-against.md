# ADR-0018: A Plugin widens the Gate table a Run is validated against

ADR-0016 placed Plugin activation ahead of the Workflow load so that a Workflow naming a Plugin's Gate would not be refused before the Plugin defining it existed. This is the ticket that uses that placement, and it settles what a Plugin's Gate kind actually is.

**The Gate table is assembled per Run and handed to the two places that need it.** `core.registry.gates_for` returns the shipped three widened by the active Plugins' validators; the runtime passes it to `load_workflow`, which validates the definition against it, and to `evaluate_gate`, which looks a kind up in it. The alternative was registering into the module-level `GATES` at activation, and it was rejected for the same reason the extractor table is passed rather than swapped (#57): a process may run two Issues, and the second one's Workflow would then be validated against the first one's Plugins. Passing the table also keeps the parser's answer a function of its arguments, which is what makes a definition's acceptance testable without a Run.

**A Plugin cannot redefine a shipped kind.** `human`, `tests`, and `security` are reserved; a validator claiming one is ignored and the shipped predicate stands. This is the opposite of the rule for Extractors, where a Plugin's reader beats the built-in one, and the asymmetry is the point. A suffix is a question about a file, and a Plugin claims one precisely where it knows more about that file than the generic reader does. A Gate kind is a promise a Workflow names: `gate: human` means the Run stops for a person, and a Plugin able to replace it could make a human Gate stop stopping — silently, in a repository whose Workflow nobody re-read. Between two Plugins claiming one kind the first in registration order wins, which is the rule `extractors_for` already applies.

**A Plugin's validator that raises becomes an errored verdict.** The wrap happens in `gates_for`, at the boundary where a Plugin's contribution enters the table, so the Run ends at the Gate with a message on its Issue naming the Plugin rather than at a traceback in the terminal of whoever started it. Errored rather than blocked, because a check that raised decided nothing and waiting would clear nothing. Shipped Gates are not wrapped: one of those raising is a defect in AgentForge, and dressing it as a verdict would hide it.

A Plugin's Gate is otherwise not a second kind of thing. It takes the same `GateContext`, which already carries the Command Runner and the working tree, so a validator that shells out to a parser has what it needs and the runtime still names no kind. It returns the same `GateEntry`, so blocked suspends and errored halts, and a verdict drawn from a Role's output names that Role in `invalidates` and un-retires that Step exactly as ADR-0008 says.

## Consequences

A Workflow naming a Plugin's Gate loads where that Plugin is active and is refused where it is not, before a Provider is invoked. The refusal lists the kinds this Run has rather than the kinds that exist somewhere, because the reader's next question is what to write instead. The cost is that one Workflow file cannot be shared unchanged between a repository the Plugin answers for and one it does not; the benefit is that a check that would never run is never silently accepted.

`--no-plugins` removes a Plugin's Gate kinds along with its Fragments and its Extractors: it means "run as if no Plugin answered", and it always did. A project whose Workflow names a Plugin's Gate therefore cannot run the #61 control against that Workflow, and will see the refusal above rather than a Run that quietly skipped a check.

`plugins/sql` ships the first validator: a `dbt` kind that runs `dbt parse`. It is the worked example the ticket asks for — parse rather than build or test, because parsing resolves every `ref()` and compiles every model without a warehouse, a profile, or data, which keeps the check within reach of a Run that has no credentials.
